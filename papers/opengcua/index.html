OpenGCUA: Toward a Fully Open Stack for Generalist Computer Use

Programs branch on intermediate results instead of executing only rigid action lists.

THE TAKEAWAY

Use intermediate execution feedback to shorten interaction loops.

KEEP IN MIND

Main results use an offline subset; fewer steps do not automatically mean lower latency or tokens.

READ / COMPLETE NARRATION

The transcript.

OpenGCUA changes how a computer agent acts. Instead of emitting a fixed sequence of clicks and shell commands, the model writes a program that can inspect an intermediate result and decide what to do next. A loop can retry, a branch can choose a different operation, and a check can verify a file before the next model call. The central idea is executable feedback-dependent control. This report releases and studies an agent system around existing models. It does not introduce newly trained model weights; a dedicated model is future work.

A harness is the software wrapper that runs tools and manages the interaction. OpenGCUA moves selected decisions from fixed harness rules to the model. The model can request a screenshot only when it needs visual evidence, track unfinished work, and state the purpose of an operation. It can combine graphical-interface actions with command-line operations inside one program. Other features, including a rolling image buffer and compacted tool outputs, remain context-management policies. These distinctions matter: giving an agent more interfaces, giving it executable control, and changing its memory management are different interventions.

The main experiment uses eighty-two offline tasks from OSWorld version two, an operating-system task benchmark. Internet-dependent tasks are excluded. Across eight models, the full system raises mean partial-completion score from 45.3 to 64.9. The average relative reduction in interaction steps is fifty-three percent. Partial score credits completed task components; it is different from full-task success. In the shown rows, GPT-6 Astra rises from 67.1 to 75.7 partial score while using 102.1 versus 33.5 steps. These are results under the paper's configurations, not a universal ranking of products.

The more revealing control keeps graphical and command-line access available, then changes how operations are coordinated. For Qwen3.8-Max, fixed batched graphical-plus-shell actions score 57.2, while code execution scores 62.4. Average steps fall from 66.1 to 54.9. Similar improvements appear for the two other models in this figure. This supports the value of a program that reacts to intermediate results beyond simply adding shell access. But this chart isolates code execution; its values are not the full OpenGCUA system's headline scores. Additional workflow and context features are evaluated separately.

On-demand screenshots also change how much context can be reused. For Qwen3.8-Max, the fraction of input tokens served from cache rises from 75.6 to 86.1 percent in that control. Yet not every added feature improves task score: intent annotations aim to explain actions to users, and scores fall slightly. More generally, fewer steps do not automatically mean fewer generated tokens or lower latency. GPT-6 Astra's output-token count rises slightly in the full comparison. Model response time, program execution time, token use, and task correctness should therefore be measured separately.

The real-device study covers only four macOS tasks, including workbook reasoning and form filling. In the selected runs shown here, GPT-6 Astra completes four and Qwen3.8-Max completes three. Qwen uses about nineteen times as many reported reasoning tokens, but only about six times as many total output tokens; those are different quantities. Four tasks cannot establish a general deployment ranking. Code can accelerate both useful work and mistakes, so authorization, complete-task verification, and recovery still matter. The research takeaway is to test executable control while preserving independent checks of what was actually completed.
